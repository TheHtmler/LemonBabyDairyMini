## 日志协议

日志前缀为 `[nutrition-timing]`，后接一条完整 JSON。`traceId` 连接一次扫描中的多个步骤，`callId` 区分每次云调用；两个编号均为无业务含义的随机字符串。

前端日志的 `source` 为 `client`，`type` 为 `span`、`milestone` 或 `cloud`。云调用中的 `server` 保存服务端返回的白名单诊断字段。

云端响应新增 `diagnostics`：版本号、扫描/调用编号、`serverElapsedMs`、`runtimeInitMs`、`handlerElapsedMs`、`firstInvocation`、`stages`、`operations`、`modelCalls`、`images`。旧版云函数没有该字段时，前端仍应正常识别并只记录客户端数据。

## 如何用真实日志定位

用户已确认实际使用开发者工具本地编译后手机扫码预览，无法从电脑控制台取得手机前端日志。可直接从开发版手机端复制：

1. 此次复制入口只修改小程序，无需再次部署云函数；重新编译并扫码预览。
2. 按原路径执行一次识别，等待结果或失败状态出现，点击浮层中的“复制耗时日志”。
3. 也可以返回拍摄页，点击“提示”→“复制耗时日志”，粘贴给排查人员。
4. 仅 `envVersion === 'develop'` 开放入口、缓存和复制；版本信息读取失败时关闭。缓存只在内存中，最多 200 条、128K 字符，导出时排除 15 分钟前的记录；退出后重新识别再复制。
5. 缓存仅包含现有白名单脱敏计时行，不写入本地 Storage，也不自动上传。保留近期多次追踪，以免遗漏双图采集或入口预检。

如使用开发者工具模拟器，仍可按原方式采集：

1. 将 `recognizeNutritionLabel`、`lookupNutritionReference` 上传并部署到当前开发环境；本轮没有代为部署。
2. 重新编译小程序，在开发者工具控制台筛选 `[nutrition-timing]`。
3. 用户按原路径执行一次识别，保留从拍摄/识别开始到结果或失败的全部计时行。
4. 正常响应时，前端日志已经包含服务端诊断，不必另行导出云函数日志；超时或没有响应时，再补同一时段云端日志。

取得日志后，将文字保存到本地文件并执行：

```bash
node "scripts/analyze-nutrition-timing.js" "/绝对路径/识别日志.txt"
```

如需合并前端、云端导出日志或限定一次扫描：

```bash
node "scripts/analyze-nutrition-timing.js" "/绝对路径/前端日志.txt" "/绝对路径/云端日志.txt" --trace nutrition_随机编号
```

- 本地裁图、压缩或上传占大头：再针对图片链路优化。
- 客户端云调用远大于服务端执行：进一步核查网络、平台调度、首次模块加载及 SDK；差额不能直接定为冷启动。
- 服务端模型接口等待占大头：结合请求字节、输入/输出词元、主备尝试和模型型号分析。
- 图片读取、鉴权、会话或额度操作占大头：针对相应 I/O 优化。
- 首轮后出现参考查询或第二次估算：分别查看这些调用，不能只看首个模型响应。
- 数值已返回但首个可用结果里程碑较晚：核查后续工作流和视图更新。

## 测量边界

- `serverElapsedMs` 从 JS 云函数入口开始，不包含进入 JS 之前的平台调度和容器启动。
- 首次执行标记仅表示当前运行实例第一次调用，不能等同完整冷启动耗时。
- 模型使用非流式响应。响应头等待包含网络和上游处理，不能当作首词元时间或纯推理耗时。
- 阶段、子操作和模型明细存在包含关系；并发图片应看墙钟时间和最慢单图，不能把明细全部相加。
- 视图更新回调是结果展示时间的近似值，不代表物理屏幕绘制完成。
- 相册的 `image.choose` 包含人工选图时间，应单独看待；它不属于模型处理。
- 首轮工作流结束后关闭该次里程碑；重试、应用准备另起计时，排除用户阅读或手填的停顿。
- 没有真实日志前，不对瓶颈、性能改善或线上版本一致性作结论。
