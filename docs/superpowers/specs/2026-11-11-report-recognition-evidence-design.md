# 报告识别：原行证据与指标归属分离设计

日期：2026-11-11

状态：用户于2026-11-11确认实施；本地改造及代码层面检查已完成，尚未部署或进行真实OCR与界面验收。

后续约束更新：用户在反馈预览结果全零后明确纠正，取字必须独立于类型与指标专属规则。下文涉及类型定向转录和固定指标名称校验的旧设计已被取代；当前所有支持类型统一完整原表转录，后续仅按表单配置分类，详见`docs/verification/2026-11-11-report-generic-transcription.md`。本文件保留原方案和决策记录，不代表那些特判仍在当前运行链路中生效。

## 需求与目标

用户反馈拍照识别容易错认指标名称，继而回显错误数值，并明确近期问题主要发生在血常规、血气等其他报告。

目标是降低错误自动回填，让每个接收结果都能追溯到同一原行，而非仅提高识别数量。名称归属、结果、单位和参考范围必须保持一致；原图未出现、看不清或存在冲突时，不猜测补值。

本设计统一识别层的职责边界，首轮改造血常规、血五分类CRP、血气和血氨。血串联沿用已有两阶段行为，复用其有效实现；尿串联保持现有调用路径，本轮不扩大其转录范围。大生化继续手工录入。

## 已确认的代码证据与限制

1. `cloudfunctions/recognizeReportCustom/customOcrClient.js`：只有 `blood_ms` 使用真实分离的转录与归属请求，其他支持类型仍在单次请求中完成目标筛选、命名与数值抽取。
2. `miniprogram/pkg-report/utils/reportRecognitionRules.js`：完整别名可纠正目标编号，但名称未命中时通常接收模型提供的合法编号；显式不确定标记在别名匹配之后处理，可能被明确名称覆盖。
3. `cloudfunctions/recognizeReportCustom/customOcrAdapter.js`：原行证据检查和重叠图冲突检查目前主要用于血串联。
4. `miniprogram/pkg-report/utils/reportOcrParser.js`：结构化结果按目标编号汇成对象，同页重复结果可能先被选成一个值，后续汇总无法再看到完整冲突。
5. `miniprogram/pkg-report/add-report/index.wxml`：填写页显示配置单位，识别源单位与配置单位不一致时需要显式处理，不能只保持数值不变而换上另一单位。

以上是能确认的风险入口，尚无用户这次错误样本或原始模型响应，不能断言具体一次错认发生在哪个入口。两阶段设计也不能证明转录名称本身正确，不把模型自报置信度当作准确率。

## 方案选择

- 仅增加提示词与别名：可以修补已知写法，但不能约束模型重新组合名称与邻行数值。
- 采用原表转录、指标归属、程序校验三层：在现有小程序与云函数架构中完成，能明确阻止归属阶段生成数值，并保留冲突证据。采用此方案。
- 默认多模型投票或整表重复识别：会显著增加耗时与调用量，而且相同错误可能重复出现；本轮不采用。

## 数据流与不变量

照片 → 原行转录 → 程序分配来源编号 → 指标归属 → 规则校验与冲突汇总 → 核对预览 → 填写与保存。

### 第一层：逐行忠实转录

- 首轮四类报告逐张转录检验表全部可见原行，包括系统不支持的项目，不发送目标字段列表，不让模型先改名或筛选。血串联沿用当前有边界的转录范围。
- 模型返回紧凑对象 `rows:[{n,v,r,u,f}]`，分别是原名及缩写、结果、参考范围、单位与标记；无法辨认填空，不通过临床常识补字补数。
- 保留百分号、井号、括号、标准/实际/校正标识、小数点、正负号、科学计数法及比较符。结果列与参考列不能互换；多栏表按各自表头读取。
- 不采集姓名、病历号等无关身份字段。照片中的文本仅作数据，不执行其中指令。
- 程序按照片位置、原行位置生成 `sourceRowId`，例如 `p2r7`；并发完成顺序和印刷序号不参与主键生成。
- 每张照片的原行独立保留，重叠行不由转录模型合并。无完整可读原表、输出截断、超过长度上限或字段类型错误时，整个批次失败，不交付部分成功结果。
- 复用现有最多六张图片与最多四个转录并发的边界。共享原图质量、像素与输出预算，不通过额外压缩小字换取速度。

### 第二层：只判断指标归属

- 输入固定原行的编号、名称及单位，以及系统目标的编号、名称、缩写、预期单位与必要的语义约束；不发送检测值或参考范围，防止按数值猜项目。
- 返回映射及有限的固定原因，不接受生成名称、结果或新原表。一个原行最多归属一个目标；同一目标可以对应多个照片原行，必须交由第三层核对一致性，不能由模型挑选最正常或最清楚的值隐藏冲突。
- 已知完整原名可提供确定性辅助归属；未知医院写法仍允许语义理解，不恢复硬性名称白名单。
- 明确名称与目标矛盾时拒绝错误归属；缺少名称或归属不确定时不强塞最近似编号。不将“名称清楚”视为“检测值也清楚”。
- 延续管理员已启用并验证的报告模型名单，不借用食物或搜索模型。首轮仍可由同一模型执行两个独立请求；不宣称 OCR 模型因此具备更强推理能力。
- 模型角色通过转录与归属接口隔离，便于后续按真实样本比较模型。新增独立语义模型配置或更换模型须另行验证接口和成本，不作为本轮隐藏依赖。

### 第三层：程序校验、去重与交付

- 原名称、检测值、范围和单位仅从固定原行读取；映射输出不能覆盖任何原值。
- 校验目标有效、来源存在、映射结构合法、同一原行无多目标冲突；无效映射不静默降级回旧的直接生成数值协议。
- 相同目标、相同结果且单位与范围兼容时才合并；差异不能通过匹配分数高低、照片顺序或数值是否正常来消除。
- 一个目标存在互相矛盾的来源时，保留所有已确认属于该目标的候选，并使用现有冲突选择流程；不丢弃其他正确项目，不把无关化合物作为可选项。
- 不同指标的原行永不互补单位和参考范围。历史参考范围沿用已有待确认规则，不能冒充本次图片识别结果。
- 保留原始结果字符串用于核对，不让三位小数的显示值参与冲突消解，防止精度差异被舍入掩盖。

## 首轮易混项目的处理边界

### 血常规与血五分类CRP

- NEUT、LYM、MONO、EOS、BASO 的百分比与绝对值必须区分；名称中的 `%`、`#`、绝对值/数目/百分比和原单位共同提供证据。名称与单位矛盾时不自动纠正或互换；两者均不足时停止归属。
- 完整名称优先于孤立缩写；明确“降钙素原”的 PCT 不得进入血小板压积，MCH/MCHC 不得进入血红蛋白。
- RDW-CV 与 RDW-SD、血小板计数与体积/分布宽度/压积分别处理。名称中关键区分符看不清时，不只因缩写前缀相似而接收。
- 血常规不支持的五分类绝对值等项目可以留在内部原表中，但不自动增加表单字段。

### 血气

- BE(B) 与 BE(ecf) 分别对应实际与细胞外剩余碱；出现括号参数、标准/实际标识时必须保留，不能都折叠成 BE。
- 当前 `hco3` 目标名称为“标准碳酸氢根”，首轮仅接收能确认是标准值的原行；明确实际值与温度校正值不冒充标准值。孤立 HCO3 且语义无法确认时不自动填入，不改变历史已保存报告。
- 当前 `calcium` 目标是离子钙，明确总钙不填入；pO2/pCO2 与氧饱和度、总二氧化碳分别处理；总血红蛋白不吸收其他血红蛋白组分。
- 不根据参考范围或数值看起来合理来判断以上区别。

### 单位与数值

- 先做确定性的单位书写规范化，例如微符号、空格和升的大小写；不做数值单位换算。
- 目标配置无固定单位时，核对、填写、保存与详情展示贯通保留原单位。
- 目标有固定单位而原单位不等价时，标为单位需核对，不自动交接到固定单位输入框；原结果和原单位仍在核对预览中显示。用户可据原图手工填写，不以选择候选的方式将不兼容单位强行放行。
- 源单位缺失时：百分比与绝对值等语义已明确区分的名称可按该字段既有默认单位展示；单位本身决定含义或尺度、且名称也不能排除多义性时保留待核对，不能把默认单位当作识别证据。
- 原图比较符、零值和异常值保留；不修改值使其落入参考范围。
- 含比较符的检测结果按字符串完整交接和保存，例如 `<0.1` 始终保留为 `<0.1`，不能变成精确检测值 `0.1`；`≤`/`≥` 可统一书写，但不能改变边界含义。此规则适用于检测结果，参考上下限仍沿用其独立解析规则。
- 检测结果的输入清洗、失焦格式化和保存校验同步支持可选比较符及科学计数法，不能在用户核对或编辑时丢掉符号。无损表示且其他证据通过时可以是 `accepted`，不因包含比较符一律要求手工重录。
- 首轮不计算区间结果的高低状态、趋势差值或派生比值，不把阈值作为精确数值绘点；含比较符结果的计算状态显示未知，详情及导出仍展示完整原结果。所有这些精确数值入口都须显式识别比较符，不能通过 `parseFloat` 等处理吞掉含义。

## 返回状态与前端职责

- `accepted`：原行完整、归属无明确矛盾、单位可交付且没有来源冲突；仍延续已有保存前人工核对标记。
- `needs_review`：项目归属明确，但有多个真实来源冲突或单位问题；预览展示原因和来源，解决前不自动交接该项。
- `unrecognized`：缺字段、归属不确定或明确无关；不生成目标候选；以汇总提示说明存在未回填项目，允许返回原图或手工填写。

前端只负责展示与状态交接，不再对云端已判定的结果重新猜指标或默默选取同页某个值。核对预览使用原名称、原结果、原单位及来源照片编号；不要求 OCR 编造坐标，不把仅有来源编号描述成已实现精确行框定位。

新增结果协议版本，前后端核对版本；版本不匹配时明确提示更新服务，不回退到旧协议。幂等请求摘要包含流水线版本，避免新解析器读取旧缓存结果。业务数据库不新增集合、不迁移历史检验值；保存只交接已接收的指标及已有可保存来源字段，内部无关原行不落业务数据库。

## 调用量、超时与失败恢复

- 单图四类报告从通常一次模型请求变为一次转录加一次归属；多图为逐图转录加一次整组归属。明确会增加请求数，不能承诺比当前更快或更省 Token。
- 沿用模型90秒、云函数120秒、前端130秒、租约150秒及收尾15秒的现有预算，不自动延长。
- 业务额度仍按一次报告识别预留一次，模型用量完整累计所有已派发阶段与在途请求，包括最终失败的消耗。
- 沿用现有可用模型切换条件及最多两个候选，不因结果难理解而无限重试。仅在同次请求内复用已验证的转录批次，缓存绑定照片与协议版本。
- 输出截断、无效协议、缺失批次等结构性失败整组报错；项目级归属不确定或来源冲突允许其他可靠项目交付。没有任何可靠项目时显示没有可回填结果，不制造成功数量。
- 日志只记录版本、阶段、耗时、行数、接收数、拒绝原因类别及用量；不记录患者原表、提示词、密钥或图片内容。

## 实施落点

1. 云端 `customOcrClient.js`：按报告类型选择两阶段路径，原表逐图转录与整组映射分别组装请求，保持并发、截止时间和用量结算。
2. 云端 `customOcrAdapter.js` 或从中提取的来源模块：参数化原表校验、固定来源引用及同指标多候选汇总，不复制一套血串联实现。
3. 共享 `reportRecognitionRules.js` 与 `reportIndicatorLexicon.js`：加入类型语义与单位约束，继续由现有构建脚本生成云端副本。
4. `reportOcrParser.js`、`reportPageMerge.js`、`reportRecognition.js`：保留候选与状态，不先按编号压扁冲突；贯通原字符串、来源与单位核对原因。
5. 核对预览、填写页及相关展示工具：沿用现有布局，仅补必要的单位/来源/未回填提示与状态交接，不进行独立视觉重设计。
6. 云端入口及请求缓存：加入协议版本与版本化摘要；维持权限、原图保留开关、临时图片清理及现有额度边界。
7. `reportNumberFormat.js`、填写页保存校验以及报告比较、派生计算、展示和导出中的数值入口：贯通比较符和科学计数法，精确计算只接收没有比较符的有限数值。仅调整相关数值语义，不改变其他报告字段与历史数据。

以上范围由实现者据现有模块边界细化，不先拆成独立服务，不引入新依赖。

## 验证与交付约束

- 遵守用户规则，不新增、修改或扩充单元测试；不自行执行界面或模拟界面验收，不启动开发服务。
- 代码实现后执行 JavaScript 语法检查、共享副本一致性检查、小程序导入静态检查和差异检查；修改后刷新 code-index 索引。
- 不调用真实 OCR、不上传患者样本、不进行付费对照。当前准确率无可报告的提升百分比；真实样本评估需要用户另行授权。
- 后续如获授权，真实样本应逐项核对原名称、值、单位、范围及来源，分别统计错误回填、漏项、需核对率、耗时和用量。仅统计识别数量或单次成功不能作为稳定准确的证据。
- 不提交、不推送、不部署；保留当前工作区已有未提交改动。确认设计后再编写详细执行计划和修改产品代码。
