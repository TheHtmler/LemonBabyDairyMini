# 首页搜索与拍照识别：现状分析、完整方案与交互规范

日期：2026-10-19。状态：方案已获用户确认，本地实现与离线检查完成；真机及真实云环境尚未验收。

本文基于当前工作区代码，包括已有未提交改动；旧设计与验收记录仅作背景，出现差异时以当前实现为准。用户已明确确认：“排查识别”指首页相机入口的“拍照识别食物／奶粉”，本方案按此范围展开。

本文保留方案阶段的现状分析与交互规范。用户随后要求按方案实现，实际业务改动、独立审查、验证结果与发布边界见 [实施验收记录](../../verification/2026-10-19-home-search-photo-experience.md)。方案阶段的浏览器预览使用演示数据，不代表真实模型、相机或数据库验收。

## 1. 推荐结论

保留“一个首页入口区域、两条独立工作流、一个共享资料库”：

- 搜索负责查已有资料、记录和指标；结果带来源、时间与计量基准，并能打开原资料或记录。
- 拍照负责把图片变成待核对的资料；先看结果，再补齐、核对、确认保存。
- 两者通过资料库和失效通知衔接：识别保存后回到原搜索，保留条件并刷新；不自动创建食用记录。
- 延用共享识别组件与当前搜索协议，集中解决交互和状态缺口，不另建一套识别引擎或搜索后端。

推荐采用“独立搜索页 + 独立扫描页 + 分步核对”。把所有内容塞入首页弹窗会叠加键盘、长表单和返回状态；把搜索变成持续聊天又会弱化筛选、来源和记录定位。当前独立页面最适合沿用，扫描页内的核对层应明确分阶段。

- 搜索通栏与独立相机点击区已经存在；公告已弱化为“查看更新”。
- 搜索、扫描分别受功能开关控制；服务端继续做实际权限校验。
- 入口分别跳转 `pkg-milk/search/index` 和 `pkg-milk/nutrition-scan/index`。

依据：`miniprogram/pages/daily-feeding/index.wxml:13`、`index.js:516`。

### 搜索

- 七类标签：全部、食物、奶粉、食谱、药物、记录、功能。
- 支持资料查询、历史记录、字段读取，以及单值、时序、对比等指标结果；具体支持范围受服务端能力白名单约束。

依据：`miniprogram/pkg-milk/search/index.js:9`、`miniprogram/utils/searchService.js`、`cloudfunctions/searchManager/orchestrator.js`；另见 `docs/verification/2026-10-19-search-cloud-cleanup.md`。

- 首页扫描使用自动模式，识别食物标签、奶粉标签或食物实物；支持最多三张图片和类型纠正。

## 3. 当前需要优先解决的问题

P0 表示本方案建议首批完成的正确性与必要交互，P1 表示随后完善的体验项；不是对线上事故严重程度的评级。

| 优先级 | 代码现状 | 使用影响 | 建议行为 |
| --- | --- | --- | --- |
| P0 | 分类按钮只过滤已加载的 `items`，目录分页每页 20 条 | 首批无某类时，不能据此判断整个分类无结果 | 分类改变服务端查询范围，并重置该范围的游标；未查完不能显示最终空态 |
| P0 | 搜索状态中有 `babyName`，模板没有展示 | 用户难以核对当前查的是哪个宝宝 | 搜索、预览、扫描和保存区域持续显示所属宝宝 |
| P0 | 输入变化使结果过期，但通常保留上下文 token | 旧 token 过期可能影响新的完整查询；新查询和追问边界不清楚 | 请求显式区分新查询、继续追问、修改条件和翻页；独立查询不用旧 token |
| P0 | 查询重试统一调用 `submit`，重新生成请求 ID | 手动条件、追问选择或翻页失败后，重试可能执行不同的查询 | 保存逻辑请求快照，重试复用原参数与适当的幂等标识 |

| P0 | 识别预览成功是 `preview` 状态，进度计算以 `ready` 判断营养完成 | 已显示结果，进度仍可能停在“等待中” | 进度由阶段事实派生；预览已就绪即完成识别，核对另列一步 |

| P1 | 资料失效后 `onShow` 调用 `clearQuery` | 拍照保存回来要重新输入问题 | 保留关键词、解释条件和来源，刷新查询；新增项不满足条件时给独立查看入口 |
| P1 | 不完整结果说明可能被有结果的列表遮住；完整依据默认折叠 | 用户只看到命中项，不知道缺项、估算或排除范围 | 摘要常显，详细依据折叠；状态提示与是否有结果分开 |
| P1 | 服务端产出 warning、evidence、字段差异／不可比原因，展示未完整贯通 | 用户知道数值，却难判断依据和冲突 | 必要警告直接展示，逐字段查看依据；不同基准不能直接比较 |
| P1 | 查重依赖同名及确认身份对象相等 | 旧手填资料、别名资料可能漏查 | 强身份命中作明确重复；弱匹配仅提示疑似重复，不能自动合并 |
| P1 | 补拍、纠正类型会重新识别 | 用户不清楚会再次等待或消耗一次识别 | 操作前用短提示说明重新识别，保留原图和原草稿到新结果可用 |
| P1 | 输入变化使预览请求过期但未同步清理 `previewLoading` | 可能留下“正在打开资料”的等待态 | 统一清理预览内容、代次与加载态 |

## 4. 页面结构与入口规则

### 首页

保留现有暖色搜索通栏：左侧“搜索食物、记录、功能”，右侧独立相机按钮；相机具备文字无障碍标签，点击不冒泡触发搜索。维持原宝宝卡、营养统计和记录入口，不在首页展开结果列表。

页面导航固定绑定进入时的账号和宝宝。切宝宝后作废所有旧结果和进行中的视图更新；已提交的保存仍按原宝宝恢复回执。

### 搜索页

从上至下：

1. 返回、页面标题、当前宝宝名称。
2. 输入框、清除、搜索按钮和相机入口。
3. 资料／记录等查询范围及类型分类；所选范围真实参与服务端查询。
4. 已理解条件：来源、日期、营养基准和筛选条件。
5. 需要补充的一个问题，或结果区；不同时展示相互冲突的操作。
6. 结果完整性说明、继续加载／重试及详情入口。

首次进入展示最近搜索和少量能力明确的示例；最近搜索按账号＋宝宝隔离，支持逐条与全部清除。键入时不逐字调用模型，提交后才执行查询。加载期间允许改写输入或返回，旧响应不覆盖新输入。

查询范围与分类的关系采用以下建议默认值，避免分类切换改变问题含义：资料列表显示食物／奶粉／食谱／药物类别；记录列表显示后端已支持的记录领域；功能结果仅显示许可的功能列表。单值、时序和对比指标隐藏资料类别标签，只保留时间、已确定的指标对象和该指标确实支持的条件。查询“上周蛋白质摄入总量”后不提供会暗中转成奶粉资料的按钮；若用户主动切换到资料范围，建立新的资料查询并清理指标上下文。首期不新增“按食物类别拆分任意指标”的计算能力。

### 扫描页

维持现有专页。能力可用后按现有首次进入策略拉起拍照，取消后停留在引导页，不反复弹相机。引导页保留“拍照识别”“从相册选择”；提示拍清名称和营养表，实物拍清全貌。

预览与核对采用同一工作流的两种视图：预览强调内容和来源，核对强调必填项和保存目标。小屏上优先使用全高页面式核对层，固定底部操作区并适配键盘；不能让遮罩、键盘和两个滚动区域争夺操作。

## 5. 搜索完整交互

### 5.1 正常查询

流程：输入 → 提交 → 解释条件 → 查询 → 结果 → 资料预览或原记录。

以“上周吃过的苹果”为例：结果区上方明确展示“饮食记录 / 上周的具体起止日期 / 苹果”，卡片展示日期、实际食用量与当时营养快照。日期解释后冻结，翻页不随当前日期变化。2026-10-19 的“上周”应展示 2026-10-12 至 2026-10-18。

以“蛋白质低于 1g 的食物”为例：如果缺比较基准，先问“按每 100 克比较吗？”；用户确认基准后执行，不能悄悄把每份、每毫升当成每 100 克。比较规则保持严格小于；真实 0 可以参与，未知不参与并提示被排除。

### 5.2 新查询、追问与筛选

- 新查询：清理旧解释上下文，重置分页和结果；独立完整问题不因旧会话过期而失败。
- 追问：通过“继续问这次结果”进入明确的继续模式，携带有效上下文；如“那昨天呢”。过期后说明需要重新查询，不能静默猜测指代。
- 修改条件：点条件标签进入对应编辑，应用后只重新执行查询，不重新解析原句。
- 切换类型：向服务端发出受控的类别调整，保留与新类别兼容的条件；若不兼容，说明将移除哪些条件，避免静默改变含义。
- 翻页：沿用同一查询解释、数据版本和日期边界；查询／宝宝变化立即清空旧游标；追加结果按稳定 ID 去重。
- 重试：保留失败操作的查询、筛选编辑、追问选择、命令或游标；网络结果未知时复用同一逻辑请求 ID 恢复，确认终态失败后的新尝试按服务端幂等契约创建新 ID，不无限复用失败回执。
- 返回：保留关键词、已应用筛选、结果、滚动位置；资料更新时刷新数据，不清掉用户意图。

### 5.3 结果展示

| 结果 | 首屏必须看见 | 点击后的动作 |
| --- | --- | --- |
| 食物、奶粉 | 名称、我的／系统、询问的字段、单位和基准 | 只读预览；明确入口进入资料管理 |
| 食谱 | 名称、配料或匹配原因 | 打开食谱；不能把模板配料当成已实际食用 |
| 药物 | 已设置的剂量／频率及其来源 | 查看现有设置或用药记录；不生成新的用药建议 |
| 历史记录 | 日期时间、实际数量、当时快照 | 定位原记录或餐次；无法精确定位时说明并打开对应日期 |
| 单值指标 | 数值、单位、时间范围、有效覆盖 | 查看计算依据与关联记录 |
| 时序指标 | 各日数据、有效天数、缺数据日期 | 切日期／查看原始依据；未知日不画成 0 |
| 对比指标 | 两组名称、相同口径、各自覆盖与差值 | 打开两侧依据；不可比较时不输出差值 |
| 功能 | 功能名称、必要的用途说明 | 打开允许访问的真实页面 |

奶粉的干粉与冲调液分别展示；不存在密度或成品体积依据时不换算克与毫升。历史结果保留当时快照，不用最新资料覆盖旧摄入。食谱严格营养筛选沿用现有支持边界，不在这一轮偷偷扩展重量体系。

### 5.4 空态与错误

- 无命中：显示实际范围和条件，提供“放宽筛选”“换个说法”；资料查询可提供“拍照添加资料”。
- 分类尚未查询完整：显示“继续查询此分类”，不能宣布无命中。
- 未知值排除：显示“部分资料缺少比较依据，未参与筛选”；允许查看解释，不将其算作满足条件。
- 网络或服务失败：显示“本次查询未完成”，保留输入和条件并重试；不展示成“没有记录”。
- AI 暂不可用：保留能独立工作的手动结构化查询；若对应后端也不可用，应真实报告，不能承诺完全离线搜索。
- 权限失效：清空当前私有结果，提示重新选择有权限的宝宝；不继续显示缓存详情。

## 6. 拍照识别完整交互

### 6.1 拍摄与处理

流程：图片选择 → 上传 → 类型／内容识别 → 参考核对 → 结果预览。

每个阶段展示真实状态，不使用虚构百分比。多图展示已上传张数。相机取消是返回引导页；相机拒绝按系统能力提示设置或相册；上传失败允许重试上传，不要求用户重新选所有图片。

类型不能确认时让用户选择“食品标签／奶粉标签／食物实物”，不允许猜测类型后直接保存。多种物品无法区分时提示一次拍一种。补图或改类型前说明会重新识别；新结果成功后再替换旧草稿，避免失败丢失已有内容。

### 6.2 结果预览

先展示：物品名称、类型、营养基准、关键营养值和来源。字段来源使用明确文字：图片识别、参考资料、手动填写、AI 估算。缺项显示“未提供”，不能补 0。

字段来源和可信度分开：有来源不等于已验证正确。对模糊读数、多个候选、单位不明等具体问题显示具体警告，不展示模型自报的“99% 准确”。支持查看原图与该字段的证据；没有精确框选坐标时仅展示图片与证据文字，不伪造高亮区域。

参考资料可用时展示来源名称与匹配身份；出现差异时逐项显示识别值、参考值、计量基准和差异原因。不同基准不能直接标为冲突。参考服务不可用时保留图片结果，标明未完成参考核对，并允许仅重试参考服务或继续手填核对。

主按钮建议由“加入食物库／奶粉库”改为“核对并加入资料库”，明确下一步尚需检查；次按钮为“关闭”。缺项不妨碍查看预览。

### 6.3 核对与补齐

- 明确“将保存到：某宝宝的资料库”。
- 食物显示名称、现有分类、单位、营养基准、必要营养及蛋白来源；扩展营养折叠为选填。
- 当前核心四项为能量、蛋白质、脂肪、碳水；食物的纤维与钠为选填，奶粉沿用现有字段契约。未知、微量或低于检出限不作为已知零保存。
- 奶粉显示当前支持的干粉营养口径和冲调参数；缺少换算依据时不能把冲调液数值直接保存为干粉数值。
- 冲调液换算干粉需要粉重与成品体积，不能用加水量替代成品体积；实物照片不能提供可靠的重量或营养实测。
- 必填规则复用现有共享契约；原型仅用已预填演示字段展示，不代表缩减真实保存校验。
- 非负有限数字、有效单位与正基准均需校验；无穷、负值、空值、错误格式不能入库。
- 缺少必要信息时主按钮不可提交，旁边明确缺哪项；用户尝试通过键盘提交时定位首个错误。
- 已改过的字段标记为手动来源；后续参考返回不能静默覆盖手填结果。
- 只有符合资格的普通食材才提供显式估算按钮；不自动估算奶粉、特殊配方或明确品牌产品。

分类保存边界也需明确：首页预览继续只选择已有分类；需要新分类时进入分类管理，明确该动作会单独保存，不宣称取消识别可撤销已创建分类。已有表单入口的分类创建是独立写入，也应有同样提示。本轮不扩展自动创建分类。

关闭核对时，如已有手填修改，提供“继续编辑／放弃本次修改”的明确选择。普通草稿虽然服务端保留一段时间，当前客户端没有关闭后恢复编辑的完整入口；本方案先保证本次会话内重试不丢稿，不把跨关闭恢复描述成现有能力。待确认保存的恢复继续使用现有持久化回执机制。

### 6.4 查重、保存与恢复

查重分两级：

1. 明确相同身份：展示已有资料，可查看；默认结束本次新增，不静默覆盖。
2. 名称接近但身份不完整：提示疑似重复，用户核对品牌、规格、段数／食物状态后决定；不做自动合并。

同名不同身份的独立资料，只有在服务端身份规则确认不同后才可新增。若要更新已有资料，进入独立且明确的编辑流程，继续校验目标版本和所属宝宝，不把“加入资料库”变成隐藏的覆盖操作。

确认保存后禁用重复提交。超时只表示“保存结果待确认”，不能直接提示保存失败；用同一幂等标识恢复回执。保存成功显示所属宝宝和资料名称，提供“查看资料”“继续识别”“返回搜索”。

从搜索进入时保存查询快照：返回后重新执行原条件。如果新增资料满足条件，定位并短暂高亮；若不满足，保持结果语义并提供“查看刚加入的资料”。不能为展示成功而硬插入不匹配结果。

## 7. 状态与交互效果规范

### 搜索状态

`空闲 → 查询中 → 待澄清／有结果／无结果／暂不可用`。

结果可带“数据不完整”标记；加载更多是独立子状态，失败不清空已有结果。新输入、范围变化或宝宝变化使旧请求失效；返回结果页不自动重复聚焦键盘。

### 识别状态

`待选图 → 上传中 → 识别中 → 待确认类型／参考核对 → 预览 → 补齐核对 → 保存中 → 已保存／结果待确认`。

上传、识别和参考服务各自提供局部重试；保存状态恢复不重新识别。识别完成与保存完成分别展示，不能用一个“成功”覆盖全部阶段。

### 动效与可访问性（建议默认值）

- 按下反馈约 100–140ms；条件与结果切换约 160–200ms；核对层过渡约 200–240ms。
- 首次结果不逐条飞入；高亮新增资料约 1.2 秒后恢复，列表位置稳定。
- 等待阶段显示阶段文案；超过约 8 秒补充“仍在处理中，可返回稍后重试”，不伪造完成进度。实际取消能力与后端请求结果分别处理。
- 键盘弹出时主操作可达，表单跳转到出错项；最小点击热区约 44px。
- 动态状态使用适当的读屏播报；错误同时提供文字，不能只用红色区分。
- 尊重减少动画偏好；大字模式允许标签换行，不挤压单位、数值与按钮。
- 普通首页方案不自动改变独立长辈首页的信息架构；如这些页面可被长辈访问，应继承可读字号和大点击区。

## 8. 技术方案与文件影响面

### 职责边界

```text
首页
  ├─ 搜索页 → searchService → searchManager
  │                              ├─ 意图／实体／计划校验
  │                              ├─ 资料、记录、指标适配器
  │                              └─ 鉴权后的结果／上下文／游标
  └─ 扫描页 → nutrition-recognition 共享工作流
                                 ├─ recognizeNutritionLabel
                                 ├─ lookupNutritionReference
                                 └─ confirmNutritionRecognition
                                              ↓
                                          资料库更新
                                              ↓
                                       搜索版本失效并重查
```

模型只提供受约束的解释或识别数据。宝宝身份、允许的功能、集合访问、营养比较、查询执行、查重与写入由代码决定。任何预览或保存都重新鉴权，不能只信前端参数。

### 搜索请求演进

继续沿用三个操作，不恢复旧接口。建议在当前 `search` 协议中增加明确的请求模式，或用同等明确的服务端规则表达 `new/followup/edit/page`：

- `new` 不读取旧上下文；`followup` 需要未过期的 token。
- `edit` 在白名单内修改类别、来源、日期和条件；不能接受任意 URL、集合名或数据库表达式。
- `page` 绑定原查询摘要和数据版本；前端不能把前一次查询游标带到新条件。
- 若新增类别编辑字段，前后端及共享契约同步更新；仅改前端 Tab 不足以完成修复。
- 协议版本是否升级按兼容性评审决定；构建标记同步更新，不能无声改变已约定字段含义。

### 识别响应与查重

把已有 warning/evidence/comparison 信息整理为前端可消费的状态与字段依据；先确认现有响应已包含的数据，尽量避免重复调用模型。必要的冲突提示进入保存校验，普通提醒不无故阻止查看或手填。

查重先在当前授权宝宝范围内做规范化名称与身份比较；只有后续测量证明需要持久化身份键时，才设计数据迁移或新索引。数据库结构和批量回填不包含在本轮分析执行范围。

## 9. 实施顺序与交付门槛

以下是建议顺序，不是当前已经执行的开发承诺，也不是工时估算。

1. **正确性收口**：分类与分页、新查询上下文、宝宝范围、预览进度、参考服务失败呈现。交付可验证的状态路径。
2. **主流程连贯**：可编辑条件、结果依据、识别核对、保存后保留搜索和定位新增项。交付双入口完整操作链。
3. **查重与异常恢复**：强弱匹配分级、保留草稿、保存结果待确认、权限与切宝宝隔离。交付异常验收记录。
4. **视觉与真机验收**：小屏、大字、键盘、相机／相册权限、弱网、后台恢复；确认前后端部署一致后再开放。

先完成前一阶段的关键验收再推进下一阶段；视觉润色不能掩盖查询范围或保存状态错误。

本轮不锁定模型型号、价格或免费额度参数。后续上线必须核对目标环境的实际配置、超时和调用限制；不能把旧文档中模型建议当成当前账号能力。重试要区分可复用结果与新增模型调用，不无限重试。

## 10. 验收清单

### 搜索

1. 首页搜索与相机点击区独立，功能关闭时呈现正确。
2. 相同关键词切换类别会查询该类别全部可访问范围，不受首批 20 条限制。
3. “上周”“近 7 天”显示明确日期，跨页不漂移。
4. 营养筛选区分 `<` 与 `≤`，未知、真实 0、微量和不可换算单位按规则处理。
5. 历史记录使用当时快照；原记录删除、迁移重复与详情失效不误报。
6. 单值、时序、对比结果显示单位、覆盖日期和依据；缺数据不当 0；指标结果不显示不兼容的资料类别，主动转查资料时建立新上下文。
7. 明确完整的新问题可在旧 token 过期后正常提交；追问过期得到说明。
8. 连续输入、快速切类型、翻页未完成时改条件，旧响应不覆盖新状态。
9. 切宝宝／账号、权限撤销后私有内容与最近搜索不串用。
10. 有结果但不完整时仍看见必要提示；请求失败不能显示成零命中。
11. 手动筛选、追问选择、加载下一页分别超时后重试仍保持原操作；追加页业务失败不清空已加载结果；预览中改输入不残留等待态；统计范围校验覆盖 90 天边界。

### 拍照识别

12. 相机取消、权限拒绝、相册选择、三张上限与上传失败均有可继续路径。
13. 食物标签、奶粉标签、实物、类型不明、多物品和模糊图分别得到正确状态。
14. 预览显示后进度不再“等待营养”；参考不可用和真实无参考能区分。
15. 数值来源、差异原因、未知值可见；无依据的干粉／冲调液换算不能保存。
16. 预览关闭不写入资料；必填不完整不保存；手填字段不被迟到参考覆盖。
17. 补图、纠正类型、重新识别失败后，原草稿与图片仍有明确恢复路径；放弃手填修改需明确选择。
18. 明确重复、疑似重复、同名不同身份与旧手填资料均有合理处理。
19. 双击保存只产生一份资料；保存超时先恢复原提交，不另建新提交。
20. 保存期间离开、后台恢复、别处切宝宝，回执仍归属于原目标。
21. 返回搜索保留条件并重查；匹配时定位新增资料，不匹配时独立提供查看入口。
