# 反馈处理结果在小程序内展示的设计

日期：2026-10-21

阶段：用户已于 2026-10-21 授权实施，本地业务代码已实现；已完成静态检查和独立代码审查修复，未部署、未进行界面或线上验收。发布配置见 `docs/miniprogram/feedback-replies.md`。

## 1. 目标与已确认范围

用户已明确：不需要微信订阅消息，直接在小程序内展示管理员回复。后续界面讨论补充：底部导航“我的”也需要显示新回复红点，让用户在其他页面就能发现回复。

本功能让用户能找到自己提交的反馈、查看处理状态和管理员说明，让管理员可以把具体处理结果传达给提交人。沿用微信小程序原生页面和现有 `feedbackManager` 云函数。

本次实施采用以下方案：

- 在现有“意见反馈”页增加“提交反馈／我的反馈”两个标签。
- 底部导航“我的”、页面内“意见反馈”入口、“我的反馈”标签及具体反馈展示联动的新回复提示。
- 每条反馈展示一份最新的管理员回复，允许管理员更新；暂不设计用户追问、聊天记录、图片附件或回复评价。
- 保留现有“未处理／已处理”两个处理状态，回复与处理状态分别表达。
- 新增一个反馈详情页，普通用户查看自己的反馈，管理员查看并处理反馈。
- 后续补充：管理员“反馈列表”入口和“未处理”筛选也显示红点与待处理数；默认按未处理状态提醒，底部“我的”汇总管理员待办和个人未读回复。查看列表不清除管理员待办。

## 2. 实施前的现状依据

- `cloudfunctions/feedbackManager/index.js`：提交时已保存 `openid`、内容、类型、提交时间和 `status`；现有操作只有提交、管理员列表、修改状态、删除。
- `miniprogram/pkg-misc/feedback/index.js`：用户只能提交，成功后约 600 毫秒返回上一页。
- `miniprogram/pkg-misc/feedback/index.wxml`：已有类型选择、最多 500 字的内容输入和提交按钮；当前没有联系方式输入框。
- `miniprogram/pkg-misc/feedback-list/index.js`：管理员列表只支持状态切换、删除，前台停留时每 30 秒刷新。
- `miniprogram/pages/profile/index.js`：普通用户入口为“帮助与支持 → 意见反馈”，开发者入口为“开发者 → 反馈列表”。

实施前的缺口是“回复内容存储、用户查询入口、阅读状态”，本次已利用现有提交人身份补齐。

## 3. 用户入口与页面

### 3.1 我的页面

保留“意见反馈”入口，普通说明改为“提交建议，查看处理回复”。有未读回复时，右侧显示红点和“有新回复”，避免仅凭颜色传递信息。

底部导航“我的”在有未读回复时显示小红点，用户停留在“今日记录”“数据记录”“报告分析”页面时也能看见。红点放在导航图标右上角，使用原生导航红点能力，不修改导航图标图片。

点击底部“我的”仍进入我的页面，不直接跳转反馈，也不清除未读。点击页面内“意见反馈”入口时，有未读回复则进入“我的反馈”标签，否则进入“提交反馈”标签。不新增全局消息中心。

四层提示共用一份未读状态：底部“我的”→“意见反馈”入口→“我的反馈”标签→具体反馈的“新回复”。打开一条回复详情后仅清除这一条的未读；其他反馈仍有未读时，上层提示继续显示。全部读完后，四层提示同步消失。

反馈归属当前微信用户，不随当前宝宝切换而变化。家人共用同一宝宝资料时，也只能查看各自提交的反馈。

### 3.2 意见反馈页

页面顶部为两个标签：“提交反馈”“我的反馈”。有新回复时，在“我的反馈”旁显示红点。切换标签保留本次打开页面时的输入草稿和列表滚动位置。

“提交反馈”保留现有分类、内容输入和按钮，说明文案增加：

> 提交后，可在“我的反馈”查看处理进度和管理员回复。

提交成功后：清空已提交的输入，展示“反馈已提交”，自动切到“我的反馈”，将新记录显示在第一项，不再自动退出页面。重复点击期间禁用提交按钮；失败时保留原文并允许重试。

“我的反馈”每项展示：

1. 反馈类型、提交时间、处理状态。
2. 原始内容摘要，最多两行。
3. 回复摘要，最多两行；未回复显示“暂无管理员回复”。
4. 未读时显示“新回复”；有回复且已读时显示“已回复”。

列表按提交时间从新到旧排列，每次加载 20 条，下拉刷新，触底继续加载；新回复用明显标记表达，不因回复更新而突然改变列表顺序。页面顶部有未读时提示“有 X 条反馈收到新回复”；X 表示反馈条数。

空列表：“你还没有提交过反馈”，按钮“去提交反馈”。加载失败应显示错误和重试入口，不能当作空列表。

### 3.3 反馈详情页

路由建议：`/pkg-misc/feedback-detail/index?id=<反馈ID>`。

内容顺序：

1. 类型、处理状态和提交时间。
2. “我的反馈”：完整原始内容，保留换行。
3. “管理员回复”：完整最新回复和回复时间。

首次回复标注“回复于”，更新后的回复标注“更新于”。回复使用普通文本呈现，不解释 HTML，不把任意输入作为链接或页面结构。

无回复且未处理：“我们已收到你的反馈，处理结果会显示在这里。”

历史记录已处理但没有回复：“该反馈已标记处理，暂无回复说明。”不凭状态编造回复，不承诺回复时限。

仅当详情成功加载、回复已显示且页面仍在前台时，提交该回复版本的已读确认。浏览列表或看到回复摘要均不清除未读。用户可下拉刷新详情。

### 3.4 视觉原则

沿用现有浅黄色页面底色、白色内容卡片和柠檬黄主按钮，回复区使用淡黄色底色并标注“管理员回复”。正文建议 28–30rpx、舒适行距，长文自动换行；状态和未读均使用文字辅助，点击区域避免过小。具体间距沿用页面现有样式，不另建一套视觉系统。

## 4. 管理员处理流程

管理员继续从现有“反馈列表”进入。每张卡片增加回复摘要和“回复用户／查看回复”入口；点击进入同一反馈详情页的管理视图。用户昵称、宝宝及设备信息等现有管理信息继续只在管理视图展示。

管理员详情在原反馈下方显示最新已发送回复，再提供“填写处理回复”输入区。已有回复时预填最新内容，并提示“保存后会替换用户看到的回复，并提示有新回复”。

输入要求：去除首尾空白后 1–1000 字，前后端一致校验；只含空白时不能保存。展示字数，示例占位文案为“例如：问题已修复，重新进入小程序后即可使用。”

两个明确动作：

- “保存回复”：将回复展示给用户，保留当前处理状态。
- “回复并标记已处理”：原子保存回复和已处理状态。

保存期间按钮禁用；保存成功显示“回复已保存”，重新展示服务端返回结果。失败保留草稿，不能显示已发送。离开有改动但尚未保存的编辑区时，尽量通过小程序页面返回提醒能力保护草稿；具体接入能力由实现阶段核对，不以本地缓存保存用户敏感反馈草稿。

保留“恢复未处理”操作。新的“标记已处理”要求已有一份非空回复；没有回复时引导“请先填写处理说明”，避免再次出现只有状态没有解释的记录。现有历史已处理记录不强制补录。

更新回复保留原始反馈内容，普通用户只看到最新回复。本方案不提供回复历史列表，也不支持清空已发布回复。相同文本再次保存不产生新的未读；如同时选择标记已处理，只更新状态。

管理员列表的自动刷新沿用现有逻辑，进入详情后列表停止刷新；详情编辑期间不自动刷新或覆盖草稿。回到列表时刷新一次。

保留已有删除能力，确认文案补充“删除后，该反馈及回复将从用户的‘我的反馈’中移除”。本次设计不执行任何删除操作；用户详情遇到记录已不存在时展示“该反馈不存在或暂时无法查看”，并可返回列表。

## 5. 处理状态与未读规则

处理状态继续存为 `new`（未处理）或 `processed`（已处理），不新增“已回复”业务状态。

- 提交反馈：未处理、无回复、无未读。
- 管理员首次保存或实际修改回复：保留状态，产生新回复未读。
- 管理员回复并完成：已处理，产生新回复未读。
- 用户读取当前回复：只清除该版本的未读，不修改处理状态。
- 管理员只切换处理状态：不产生回复未读。
- 管理员再次更新回复：版本递增，再次提示新回复。

更新提示在小程序启动且身份就绪、回到前台、底部导航页面进入或切换、反馈页面进入或返回、下拉刷新时触发，用户端和管理员端均不使用定时轮询或后台常驻监听。管理员列表原有的 30 秒定时刷新已按用户后续要求移除。因此收到新反馈或回复后，已停留的页面不会承诺实时变化；刷新、切换页面或重新进入即可看到。

未读数量及导航红点由共享模块统一管理，不只在“我的”页加载。身份就绪后读取未读数量；冷启动、回到前台和手动下拉刷新强制更新，同一用户 30 秒内的普通页面切换可以复用内存结果，同一时刻复用正在进行的请求，避免多页重复调用。

阅读成功后立即更新已读反馈和共享未读状态，重新确认未读数量，并同步底部导航红点；本机管理员保存回复后使相关缓存失效。旧请求返回时不得覆盖较新的已读结果。列表、详情和未读摘要共享失效通知，但不保存跨用户结果。刷新失败保留已有结果，不把错误当作未读数归零。

未读状态在导航栏尚未显示时也可更新，待底部导航页面显示后重新应用红点。用户切换身份或退出时清除导航红点，待新身份查询成功再显示。长辈模式中底部导航隐藏时不强行显示，退出后按当前未读状态恢复。底部“我的”未来若增加其他业务红点，应统一汇总各来源，不能由反馈模块清除其他来源的提示。

## 6. 数据设计

继续使用 `feedback_messages`，不另建聊天或消息集合。在现有记录上新增：

| 字段 | 含义 |
| --- | --- |
| `replyContent` | 最新回复正文，默认空字符串 |
| `repliedAt` | 最近一次回复内容实际变化的服务端时间 |
| `repliedBy` | 最后回复的管理员身份，仅服务端及管理视图可用 |
| `replyVersion` | 回复版本，默认 0；正文实际变化时递增 |
| `readReplyVersion` | 提交者已读版本，默认 0 |
| `hasUnreadReply` | 是否有新回复，服务端维护，便于查询和统计 |
| `lastReplyRequestId` | 最近一次成功保存回复的请求标识，用于重复请求去重 |

一致性条件为：`hasUnreadReply = replyVersion > readReplyVersion`。用户端不能直接写这些字段。

历史记录缺失字段时按“无回复、版本 0、无未读”解释；已有 `openid` 可用于显示历史反馈。采用读时默认值和写时补齐，不进行批量数据迁移；缺少有效提交人身份的异常记录只允许管理员查看，不猜测归属。

保存回复、版本递增、未读标记，以及可选的已处理状态必须在同一事务内完成。保存携带基于加载结果的 `baseReplyVersion`；如果其他管理员已经修改过回复，返回冲突并保留当前草稿，要求刷新后重新确认，不能静默覆盖。

同一次保存操作生成并复用 `requestId`。同请求重试应返回成功，不重复递增版本；如果记录已有后续回复，则按版本冲突处理，不重放旧文本。相同正文不递增版本，去重只针对当前最近一次请求，不额外建立完整请求历史。

标记已读必须携带实际展示的 `seenReplyVersion`：服务端检查为合法整数且不大于当前版本，在事务中把已读版本提升到已展示版本与已有已读版本中的较大值，重新计算未读。若用户看到版本 1 后管理员已发布版本 2，则确认版本 1 不能清除版本 2 的提示。

## 7. 云函数接口与权限

在现有 `feedbackManager` 上增加以下动作，具体参数封装由实现阶段按项目风格落地：

| 动作 | 调用方与主要规则 |
| --- | --- |
| `listMine` | 当前用户自己的反馈列表，20 条一页，服务端固定按身份过滤 |
| `getDetail` | 提交者可读自己的详情；管理视图必须另外校验管理员资格 |
| `getUnreadCount` | 仅统计当前用户 `hasUnreadReply = true` 的反馈条数 |
| `saveReply` | 仅管理员；接收反馈 ID、正文、保存模式、基础版本、请求 ID |
| `markReplyRead` | 仅反馈提交人；接收反馈 ID 和实际展示版本 |

现有 `submit` 增加默认字段并补齐服务端内容长度校验；`list` 保持管理员专用并增加回复摘要；`updateStatus` 增加“标记已处理前需有回复”的服务端规则；`delete` 维持管理员权限。

管理员的唯一授权依据为云函数中现有开发者白名单。客户端的 `isDeveloper`、路由参数、用户角色和宝宝创建者身份均不能授予管理权限。

用户查询以云函数取得的 `OPENID` 为准，不接受客户端指定查询其他人的 `openid`。详情接口区分普通与管理视图：请求管理视图必须经服务端校验；管理员通过“我的反馈”查看自己的记录时也使用普通视图，只有提交人自己的普通查看流程会确认已读。

普通用户响应采用字段白名单，仅包含反馈 ID、类型、本人内容、状态、提交时间、回复内容、回复时间、回复版本和未读信息；不返回管理员身份、提交人身份标识、设备信息、联系方式和其他管理元数据。管理员浏览别人的反馈不会清除提交人的未读。

新列表使用稳定游标分页：`createdAt` 降序并以 `_id` 作为相同时间的排序补充，游标仅作定位条件，不能覆盖身份条件。缺失有效 `createdAt` 的异常记录不参与普通列表，记录诊断信息，仍可由管理员查看；正常历史提交路径已写入 `createdAt`。

部署时为按 `openid` 查询并按 `createdAt`、`_id` 排序，以及按 `openid`、`hasUnreadReply` 统计准备必要索引；准确索引定义根据云数据库执行计划和实际要求核对。数据库权限应禁止客户端直接读取他人反馈或直接改写回复，统一走校验后的云函数。当前仓库未检索到对应集合规则文件，不能认定线上规则已经满足要求；实施时需单独检查和准备配置，发布配置变更前遵守用户确认规则。

## 8. 异常与边界

- 身份尚未就绪：显示加载态，不以空身份查询；失败提供重试。
- 详情加载失败：不标记已读，重试成功后再确认阅读。
- 已读确认失败：仍允许阅读；保留未读提示，后续重新进入可重试，不谎报同步成功。
- 读取旧版本期间出现新回复：旧版本已读确认不吞掉新提示；如果响应提示仍有更新，详情显示“有新回复，刷新查看”。
- 管理员保存超时：保留文本、请求 ID 和基础版本，重试按同一请求执行。
- 管理员并发更新：明确提示“回复已被更新，请刷新后重新确认”，当前编辑内容保留至用户主动放弃。
- 数据不存在或权限不符：普通用户收到统一提示，不泄露其他反馈是否存在。
- 删除与保存并发：以服务端事务结果为准，不把已删除反馈重新创建出来。
- 用户切换身份或退出：清除对应内存缓存及当前页面数据，旧请求返回时不得写入新身份视图。
- 长回复、换行和特殊字符：按文本原样展示，长度上限以统一计数规则执行，前后端保持一致。
- 长辈模式保持现有导航规则，退出长辈模式后从“我的”使用反馈；本次不扩展长辈首页入口。

不改动现有订阅消息配置、喂养提醒流程或账号权限模型。

## 10. 实施与验收标准

建议先完成云函数数据和权限逻辑，再接用户列表及详情，然后接管理员回复和未读入口。先部署兼容的云函数和必要配置，再发布小程序页面；发布、数据库规则或索引调整不包含在本次设计任务中。

必须满足的业务结果：

1. 普通用户能看到本人历史及新提交反馈，无法读取其他人的记录。
2. 管理员保存后，用户刷新或重进即可看到对应回复。
3. 用户看到的状态、回复及时间来自同一份服务端记录。
4. 摘要浏览不会误清未读；读取旧回复不会吞掉后来的更新。
5. 拒绝越权回复、空回复、超长输入和无效版本参数。
6. 网络失败、重复保存和并发更新不丢失草稿、不重复产生新回复。
7. 历史无回复记录可正常显示，不需要批量修改已有数据。
8. 在“今日记录”等其他导航页面也可看到“我的”红点；进入我的页面本身不清红点；部分已读仍保留总提示，全部已读后各层提示同步清除。

验证遵守用户约束：默认不新增、修改或扩充单元测试；实施时执行语法、静态检查及项目可用的构建检查。权限和并发先做代码走查；上述业务场景为后续验收目标，不代表已实测。界面操作、浏览器自动化、截图及为验收启动服务，都必须事先说明范围并取得用户明确同意。
