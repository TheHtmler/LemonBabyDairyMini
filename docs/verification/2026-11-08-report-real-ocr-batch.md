# 报告识别：真实四图对照与整份联合识别

日期：2026-11-08
分支：`codex/recognition-image-retention`

## 授权与数据范围

用户明确允许将原先四张报告调用当前配置的千问 OCR 做真实对照，并在本机临时文件中填写凭据。本轮没有进行界面操作、创建报告、写生产数据库、提交、推送或部署。

使用 IMG_9857～IMG_9860 四张原始 HEIC，在本机通过 libheif 转为质量 95 的 JPEG，大小约 3.5～3.8 MB，均处于现有单图 6 MB 限制内。凭据、原始模型响应和完整检验数值只保留在权限受限的本机临时目录，未写入仓库。

## 真实结果揭示的根因

- 原先的单图定向提取连续调用四次，服务均成功响应，但最终只有 2/6 项的数值和参考范围全部正确，产生 3 个冲突；另一个直接展示的项目数值不正确。
- 原始响应不仅错误归类，还将其他行的项目名称改写为目标名称。因此，即使返回名称命中词典，也无法证明它就是原图该行；上一轮的名称证据优先规则不能修复这种模型错误。
- 对出错的局部照片分别尝试无目标名单的逐行转录及原生表格解析，保住了部分名称，但倾斜、截断的表格仍出现跨行配值问题，未作为产品方案采用。
- 将四张照片作为同一份报告放入一次请求后，模型可使用重叠区域和完整报告上下文，实验请求得到 6/6 项正确结果。实际产品代码完成修改后再独立请求一次，也得到 6/6 项正确的数值与参考范围、0 个冲突。

## 最终实现

1. `customOcrClient.js` 使用 `buffers` 数组，一次请求携带 1～6 张图片，保持照片顺序，将图片放在指令前；指令要求综合一份报告的所有部位、利用重叠区域、沿印刷行方向读值，每个目标采用最清楚的实际原行。未更换模型或 API 地域。
2. `imagePayload.js` 对整组云文件逐一校验宝宝归属、当前云环境、数量、重复文件及实际图片格式；下载不完整时不发送模型请求。请求摘要绑定报告类型、每张图片内容及顺序。
3. `recognizeReportCustom/index.js` 接收 `fileIDs` 数组，完成一次业务权限校验、额度预留和模型请求；结束时清理整组已校验的临时文件。日志仅记录张数、字节数、解析版本和数量统计。
4. 前端 `recognizeReportPhotos` 上传整组图片后调用一次云函数，失效、异常和超时都会清理已上传的临时图片。
5. 识别页保存一个属于整组照片的结果。增删照片会作废旧结果和选择，重新识别整组；失败时重试整组，避免把失去上下文的单页重新塞回旧结果。账号或宝宝切换后不交付失效结果。
6. 页面等待文案显示正在识别的图片张数，不再展示逐页独立识别的完成比例。没有新增页面或交互入口。
7. 额度仍按实际模型请求预留：一份报告的 1～6 张照片一次联合请求计一次业务次数，增删后重新请求也计一次。管理员说明同步更新，限额数值没有修改。模型图像 Token 仍按所有输入图片累计，并不会变成单张图片的费用。
8. 解析版本为 `qwen-report-v5-report-batch`，前端调用协议改为 `fileIDs`，未保留旧的逐图调用分支；两端需要同步更新。

## 验证

- 正式代码真实四图回归：6/6 项数值及参考范围正确，0 个冲突，约 21.2 秒；关键项目均逐一对照原图，没有按数值是否正常筛选。
- 本轮诊断共 8 次成功模型请求，包括单图基线、两种单页探测、联合实验及正式联合回归；返回用量累计 180,139 Token。临时诊断直接调用用户授权的模型接口，没有写应用业务次数计数或报告数据。
- 新增 `tests/report-batch-recognition.test.js`，覆盖一次请求包含全部图片及顺序、单张/六张边界、越界/无效输入、跨宝宝/跨环境文件、整组内容摘要、下载失败与格式错误。新增用例先失败，再实现通过。
- 六个相关纯函数测试文件共 144 项通过。没有执行页面加载、模拟微信交互或界面验收。
- `npm run build:search`、`npm run check:search`、相关 JS 语法检查及 `git diff --check` 通过；模板 37 处表达式语法和 7 处事件绑定检查通过。未执行微信原生模板编译器或真机验收。
- 修改后刷新代码索引；云函数原有 60 秒超时、512 MB 内存配置保持不变，模型等待仍限制为 45 秒。

接口依据：[千问 OCR 官方说明](https://help.aliyun.com/zh/model-studio/qwen-vl-ocr)。本次四图请求真实成功的响应同时验证了当前模型与配置可接受这一输入组合。

## 发布与限制

需完整部署 `recognizeReportCustom` 并更新小程序，包括生成的 `lib/report` 和 `lib/config`。本轮没有部署。旧客户端仍传单个 `fileID`，与新版云函数的组协议不同，应同步发布两端。

两次联合请求成功仅验证这份报告的四张照片，不能推广为所有医院、图片质量、六张大图组合或报告类型均保证准确。真实云函数上传下载、生产额度链路及界面交互仍未验收；应避免将本次模型接口回归表述为全链路真机验收。
