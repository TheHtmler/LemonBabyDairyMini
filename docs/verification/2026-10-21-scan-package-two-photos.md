# 拍照识别：包装双图与实物营养预览

## 本轮范围

- 左上角标题使用 16px；返回箭头缩小视觉尺寸，保留 44px 点击区域，沿用微信胶囊中心对齐。
- 食物默认单张拍摄，包装食品可切换“双面拍”；奶粉默认双面拍。依次收集营养表和正面图，每次相册只选一张，拍齐后统一识别。
- 点击图片位置可替换该面；取消相册选择保留已有图片；切换拍摄方式、食品类别或宝宝时重置图片位置。
- 移除结果页补拍和重新提交全部图片的确认流程，未识别字段可重拍或手填。
- 正面图用于结果背景；保存食物时上传到 `food_images/`，避免展示图随临时识别草稿过期清理。奶粉档案没有食物图片字段，不额外保存该图片。
- 移除预览、应用表单中的食物状态选项及关联处理函数。内部仍使用图片自动识别的生熟状态；未知时不默认生鲜、不强迫用户填写。

## 慢与实物营养缺失的代码结论

1. 旧链路在实物模型返回后继续等待参考查询。现在首轮完整估算直接用于预览，正式参考比较与版本绑定在应用时执行；预览不能绕过保存校验。
2. 旧模型输出重复包含食材名称、状态、每 100g 基准及各指标单位，重复身份有可能因为名称不一致而被拒绝。首轮实物估算改为紧凑数值结构，服务端绑定唯一识别身份与标准单位，并继续检查数值范围和营养总量。
3. 提示明确食材别名放入 aliases；实物依据是外观特征，不要求印刷文字；切开、去皮、冷冻不等于烹调。这些都是通用规则，没有牛油果专用分支。
4. 首轮缺估算且无参考值时，仅对明确身份、状态、基准的普通食材自动尝试一次补充估算。此异常路径仍可能增加等待，并按现有服务规则消耗一次额外模型调用额度；不会对包装标签或身份不明食物猜数值。
5. 名称先显示在浮窗，后续营养处理显示“读取中”；结束后缺失字段显示“未识别”。参考查询失败时保留已有有效预览值，估算失败时允许重试或手填。
6. 两张图片并发上传，返回数组仍按原位置排序，保证模型证据序号对应正确图片。

无法仅凭本地代码确定用户这次十几秒中模型耗时所占比例，也未对用户图片做真实模型请求。现有 `[nutrition-timing]` 记录上传后各云函数及模型阶段耗时；新增估算接纳日志只记录状态、候选数量和制备状态，不记录图片、名称或密钥。
