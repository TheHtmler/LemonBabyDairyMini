# 报告识别输出上限处理记录

## 现象与判断

用户再次反馈「第4张图片取字，识别原行缺少名称或结果」。该提示属于结构校验失败，单凭提示不能确认截断。此前真实日志已经明确出现两张图片 `finishReason=length`、`outputTokens=4096`，说明单次整图输出确实会触顶。v16只压缩JSON格式，不能解决任意长报告的单次输出上限。

本次改为内部版本 `qwen-report-v17-segmented-source`，外部交付协议继续使用 `report-evidence-v2-generic`。请求摘要包含内部版本，旧缓存不能复用。

## 实现与边界

- `imagePreprocess.js` 使用 sharp 实际解码、按EXIF归正并裁图，不缩放文字。核心区域按高度及约200万像素预算预分块。
- 核心范围连续覆盖原图；上下文至少为核心高度的一半或原图宽度的15%，取较大者。继续二分核心时保留宽度相关上下文，减少倾斜和换行项目被切断的影响。
- 两侧额外增加16像素白边，蓝色竖栏只标记核心，不覆盖报告文字。取字按原名称文字中心归属，只输出核心行，可以借上下文读全跨界行。范围内真实行仍读不全时保留一行，对不完整单元填null，不能使用半段名称、半段数字或补0。
- 优先返回PNG；拍照JPEG转PNG可能膨胀，PNG超过6MB时才采用同像素、质量98、4:4:4采样的JPEG。JPEG仍过大时继续拆分，不能静默降低分辨率。JPEG属于有损编码，不能将这条兜底路径描述为全程无损。
- 任何模型输出截断、原行结构不合格或图片块体积超限，均丢弃该次不完整输出，仅将当前核心二分。最多追加3层，最小核心128像素；达到边界仍失败时明确返回失败及分块路径。
- 最多4个模型请求并发，图像原生解码串行，sharp缓存16MB、工作线程1。每张输入最多2400万像素、单帧；原始上传仍受原有6MB限制。
- 所有图片叶块成功后才按照片和核心位置排序，生成固定来源编号。保留重复原行；不按指标名称、数值或完成顺序去重。
- 分类每批最多32行，只发送编号、原名、原单位和现有表单目标。分类结果超限或结构异常则继续二分，最多拆至单行；全部成功后统一校验和生成回填结果。
- 图像取字不接收报告类型，也没有医学指标专属字段规则。报告类型仅用于后续分类。
- 总模型阶段仍共用90秒和本次最多96次调用预算，切备用模型不重置预算。成功的叶块和分类批次只在本请求内缓存；终止失败后等待在途请求，累计已返回的用量，不交付半份成功。
- 日志增加 `segmentPath`、`segmentDepth`、`mappingPath`、拆分原因及总调用数，禁止输出检验原文、图片和提示词。前端错误区分照片分块及分类批次。

## 部署前提

新增原生图像依赖，部署时需使用Node.js 20.19或更高受支持版本，并由目标Linux云环境安装依赖及可选依赖；不能上传Mac的node_modules替代云端安装。当前没有修改实际云运行环境，也没有部署。sharp要求Node-API v9（例如Node.js>=20.9.0），Linux x64预编译包要求glibc>=2.28及SSE4.2，需在实际云运行环境确认。
