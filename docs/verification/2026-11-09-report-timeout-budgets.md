# 报告超过60秒后的超时预算修正

日期：2026-11-09

## 证据与范围

- 用户先描述实际等待超过60秒且日志有 `timeout`，因此按超时方向排查。随后提供的实际日志为 `INVALID_MODEL_RESULT`、`httpStatus: null`，不是超时错误；此前据描述确认超时的结论证据不足，需要纠正。尚未取得独立的超时日志，本记录的预算调整不能作为这次失败原因已查明的依据。
- 原模型预算为调用开始后的45秒，云函数执行配置60秒，前端等待70秒。权限校验、四图串行下载、额度处理、结果落库与临时图清理不在45秒模型预算内，累计后可能碰到60秒上限。
- 上一轮已将旧模型的四图重复归属请求缩为一张参考图。本轮继续减少预处理等待，并把时间预算作为一套配置维护，没有再次发送报告图片。

## 本地改动

- 图片下载改为最多六张并行；保留原顺序、原始字节、逐图校验及整组摘要。任何图片失败时仍不发送不完整图片组给模型。
- `REPORT_OCR_TIMING` 统一模型90秒、云函数120秒、前端130秒、报告请求有效期150秒，并为模型后处理预留15秒。
- 模型截止时间取“模型开始后90秒”与“函数开始后105秒”中的较早时间；预处理占用过多预算时，在模型派发前返回准备超时，避免无剩余时间仍发起付费请求。
- 额度预留继续只计一次业务调用。报告传入150秒有效期，使超过60秒但仍在处理的同请求继续返回 `AI_RUNNING`；其他场景默认60秒有效期保持原样。
- `recognizeReportCustom/config.json` 本地执行配置改为120秒，前端读取同源时间常量。构建脚本校验函数配置及预算层次，避免只改前端或只改模型等待时间。
- 增加权限校验、下载、额度预留、派发、模型、落库及清理阶段的开始日志和耗时。硬超时前最后的 `[report-ocr-stage]` 可定位停在哪个阶段；正常结束记录 `[report-ocr-finished]` 总耗时。
- 日志只含固定阶段、错误类别和数字耗时，不写报告原文、密钥或图片内容。数据库写入仍等待完成，不用超时竞速抛弃正在执行的额度事务。

## 验证与部署要求

- 沿用用户已授权的离线报告流程测试范围，新增并行下载乱序完成、函数收尾时间预留、模拟60秒后继续归属、延长请求有效期及其他场景默认有效期用例。修正前相关用例失败，修正后11个相关测试文件共188项通过。
- `npm run build:search`、`npm run check:search`、相关 JavaScript 语法检查与 `git diff --check` 通过，代码索引已刷新。
- 未进行界面或模拟页面验收，未调用真实付费模型，未部署、提交或推送。增加等待预算并不代表真实识别耗时或完整性已验证。
- 生效需完整部署 `recognizeReportCustom`（包含 `lib`、配置和代码），在云端控制台确认实际执行超时为120秒，并更新小程序。前端 `Promise.race` 只负责本地等待，不能修改云端实际执行配置。
- 云端仍可能因平台通道限制或某个SDK操作长期等待而失败；完整超时日志及新增阶段日志仍是判断实际原因的必要证据，不保证扩大预算能解决所有超时。
