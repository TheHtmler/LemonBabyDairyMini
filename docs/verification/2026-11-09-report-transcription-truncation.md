# 血报告第一阶段转录输出截断修正

日期：2026-11-09

## 证据与原因

- 用户补充实际错误为 `MODEL_OUTPUT_TRUNCATED`，阶段为 `transcription`，因此本次发生在原表转录，尚未进入指标归属，不能继续归因为超时。
- 所提供日志中，下载阶段约4.1秒，模型阶段约47.8秒，总计约52.7秒后进入失败处理。耗时较长与输出截断同时存在，但耗时本身不是判定超时的依据。
- 原请求把四张血报告图片放在一次转录中，共享一次模型输出额度。当前使用的旧版 `qwen-vl-ocr` 系列受既定输出上限约束，继续提高 `max_tokens` 会再次触发请求参数错误；本次通过拆分输入降低单次转录输出量。

## 本地修改

- 仅对旧版 `qwen-vl-ocr` 系列的多图血报告，改为每张图片独立转录，最多两张并行，保留单图像素预算与共享的整次模型截止时间。
- 提示词明确只转录本次实际提供的图片，使用紧凑JSON；图片内的文字指令仍作为文档内容处理。
- 等全部图片转录完成并通过校验，再按原图片顺序汇总固定原行，并一次完成指标语义归属。不同图片局部印刷行号允许相同，由程序生成带照片来源的唯一行号，不重写名称或检测值。
- 重叠照片中相同读数按数值、范围和单位兼容性合并，保留多源行号与更完整字段；不同数值、矛盾参考范围或不同单位拒绝静默覆盖，返回固定的 `SOURCE_VALUE_CONFLICT` 诊断。模型仍可理解未收录名称，别名没有变为白名单。
- 任意图片响应截断或无效时，停止派发后续图片，等待已在途调用结束以累计用量；不解析半份JSON、不交付部分报告，也不继续归属。
- 并发请求各自保留阶段和图片批次诊断；跨图汇总失败补充 `source_merge` 阶段。失败日志改为单行JSON，便于完整复制阶段、模型、用量与耗时，未增加报告正文或图片内容。
- 新版模型仍沿用整组转录与独立归属；尿报告调用方式保持原样。解析器版本为 `qwen-report-v9-paged-blood`。

## 用量与验证

- 无备用模型切换时，旧模型四张血报告由原来的两次请求改为四次逐图转录加一次归属，共五次模型请求；业务额度仍只预留一次，模型Token用量按全部实际响应累计。请求数增加，不能据离线结果推断真实费用或延迟下降。
- 沿用用户已授权的离线报告解析测试，覆盖最多两张并行、乱序完成、全部转录完成后才归属、重复行号、相同读数合并、来源传递、矛盾读数拒绝、截断后停止派发及在途用量结算。新增汇总诊断用例先复现缺少阶段字段，修正后通过。
- 十二个相关离线测试文件共200项通过；`npm run check:search`、相关JavaScript语法检查和 `git diff --check` 通过。
- 用户此前已暂停付费验证，本轮没有调用真实OCR、发送报告图片、进行界面或模拟页面交互验收，也没有部署、提交或推送。

## 生效要求与限制

- 需完整部署 `recognizeReportCustom`，包括 `lib`、配置和代码；云端执行超时仍需与本地配置120秒一致。更新小程序代码以保留多源行号元数据。
- 部署后可用日志中的 `parserVersion`、`sourceBatchCount`、`transcriptionMs`、`mappingMs` 核对实际运行路径；失败时可按 `stage`、`batchIndex`、`batchCount` 定位图片请求。
- 单张图片仍可能超过模型输出上限或被漏读；此时继续明确失败，不将离线流程通过表述为真实识别完整性已验证。
