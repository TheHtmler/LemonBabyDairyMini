# 血串联识别：氨基酸错配与亮氨酸漏项

日期：2026-11-08
分支：`codex/recognition-image-retention`

## 原图与截图核对

本次核对用户提供的四张血报告 IMG_9853～IMG_9856 和结果截图 IMG_9877，没有进行界面操作。

- 截图中的精氨酸数值和参考范围对应原图首行丙氨酸，实际精氨酸在第二行。
- 截图中的甲硫氨酸数值和参考范围对应原图亮氨酸，实际甲硫氨酸在下一行。
- 亮氨酸本身没有出现在识别结果中；它属于系统现有的异亮氨酸/亮氨酸字段。
- 缬氨酸、C0、C2、C3、C3/C0、C3/C2 的截图值与原图一致。原图没有苏氨酸目标行，不应为了凑齐字段补值；这份报告应保留九个受支持目标项目。
- 截图照片顺序与原始文件编号相反，真实回归应先按截图顺序验证，避免仅验证另一种顺序。

为避免把患者检验数据写入仓库，本记录不列出全部数值；本机临时诊断脚本保存人工核对的预期值，并准备捕获模型原始响应。

## 最初复现的程序缺口

1. 原词典包含亮氨酸中文名，但缺少 `Leu`。完整原名“亮氨酸(Leu)”无法通过同一指标的名称证据匹配；如果模型给了错误的 `met` 编号，代码会接收，不能纠正到 `iso_leu`。
2. “丙氨酸(Ala)”没有被识别为与精氨酸矛盾的明确来源。如果模型误给 `arginine` 编号，代码会接收这条无关原行。
3. 模型提示词缺少血报告中 Arg/Ala、Met/Leu 以及系统合并字段与原图单列 Leu 的具体对应说明。

以上校验缺口已修正，但真实对照表明它们不是本次错行的全部原因：模型在原始响应中已返回目标名称配邻行数值，单靠名称校验无法发现。

## 第一轮修正（v7）

- 在原有词典中补充 `Leu`、`Leucine`，完整中文名与括号缩写可作为名称证据，纠正错误模型编号；没有恢复名称硬白名单，未收录名称的明确模型归属仍保留。
- 扩充既有精氨酸相似来源检查，将丙氨酸、Ala、Alanine 等明确其他项目排除，避免错填到精氨酸。
- 血串联改为原行证据协议：模型先转录原表行 `rows`，再返回只包含目标编号与原行编号的 `matches`。映射阶段不能携带新名称或新数值，程序只从对应原行读取名称、检测值、单位和参考范围。
- 原表转录保留氨基酸浓度区的非目标项目，避免只输出目标时把丙氨酸改名为精氨酸；另外转录所需的 C0、C2、C3、C3/C0、C3/C2 原行。控制输出范围，避免完整转录全部非目标行造成超时。
- 校验唯一行号、引用必须存在、每行字段结构与长度、同一行不能映射多个不同目标。拒绝血报告旧的直接生成指标值协议，避免新提示词失效时继续接收缺少原行证据的结果。
- 原行名称证据明确时仍能辅助找回漏映射的项目；名称未收录但模型映射明确时仍保留，没有恢复名称硬白名单。程序不会为原图没有的苏氨酸补值。
- 云端结构化结果保留 `sourceRowId`，前端解析继续保留该编号，便于追溯。前端页面及云函数调用协议不变，仍是一份报告多图一次模型请求。
- 尿报告及其他类型继续使用此前已验证的结构化抽取协议；对照修正前代码快照，尿报告请求体逐字一致，没有再次消耗模型额度重复相同请求。
- 云端与前端通过现有构建脚本同步同源词典。解析版本更新为 `qwen-report-v7-row-evidence`。提示词不包含患者检验数值，超时、内存、模型和额度配置均未修改。

## 当前本地改动（v8，尚未真实验证）

- 将血报告拆成两个实际模型请求：第一阶段只看整组图片、转录原表，不提供系统目标列表；第二阶段只接收第一阶段表格文字与目标定义，理解指标归属，不能改写原行名称或数值。此前把两步写在同一个提示词中，模型仍会跳过第一步而只输出目标行。
- 第一阶段立即校验原表字段、唯一行号与长度。第二阶段返回的其他原表数据不会覆盖第一阶段证据，重复或不存在的行号映射继续拒收；没有恢复缺少原行证据的旧协议。
- 修正一个独立确认的漏项分支：血报告原行名称和结果明确时，空的模型归属不再删除该行，仍按完整原名证据找回；未知名称或 Leu/Phe 等比值不会由此补成亮氨酸。尿报告的显式空归属语义保持原样。
- 两阶段共用同一个 45 秒截止时间，不自动重试或延长预算；空原表不发起第二请求。一次报告业务调用仍只预留一次额度，模型 Token 用量累计两阶段；第二阶段失败时，第一阶段已消耗用量也交给既有计费记录处理。
